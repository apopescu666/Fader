# Net Share prototype 0.6.8.2 verification

## Final 0.6.8.2 checks

- **Folder-switch stability**: the folder-switch crash reported on the TCL was attacked from several directions at once, without changing SMB, credentials or the playback engine:
  - `android:largeHeap="true"` gives the app a larger Java heap for big-library metadata (576 MB heap limit on the API 37 emulator instead of the previous 192 MB growth limit).
  - The library cache is capped by total tracks (`LIBRARY_CACHE_MAX_TRACKS = 24,000`) and keeps at most 2 folders; a single huge folder is not retained in memory.
  - `ArtworkStore` keeps only **one** in-memory folder metadata index, capped at **8,000 entries**, refuses index files above **6 MB**, and catches `OutOfMemoryError` while loading an index.
  - `completed` metadata entries are capped at 4,000; the image LRU stays at 32 MB; embedded pictures are limited to 8 MB and down-scaled to 512 px.
  - `MediaMetadataRetriever` is serialized with a process-wide lock because it is not thread-safe on several TV chipsets and can crash in native code when four readers use it at once.
  - `OutOfMemoryError` is caught in quick browse, recursive browse, **Play all** and the artwork workers; the app frees caches and shows a status message instead of closing.
  - The `Visualizer` is detached **before** the old `MediaPlayer` is reset/released; `release()` also resets first, and the SMB source close stays off the main thread.
  - The folder list keeps the previous playlist visible with **LOADING…** while an opened folder has only subfolders and the recursive scan has not produced songs yet, instead of blanking the right panel.
- **Diagnostics**: Settings now shows **Memory: x MB used of y MB** and, after a Java crash, a **Last crash** row with the timestamp, device, memory and stack trace. Native crashes and low-memory kills cannot be captured by a Java handler, but the row makes Java OOM/`IllegalStateException` visible without adb.
- **Emulator verification (API 37, 1920×1080)**: with a track playing over SMB, `Music → Album → Music` was repeated three times with a song loaded from the new folder each time. The process PID stayed `7609`, playback continued across every switch, the cover and metadata appeared, and logcat contained no `FATAL EXCEPTION`, `FaderCrash`, `OutOfMemory` or `AndroidRuntime` entry for the app. Opening a nested `Deep` folder (subfolder only) kept the list usable and showed the recursive song after the scan.
- **Settings**: showed `Memory: 6 MB used of 576 MB. largeHeap is enabled for big libraries.` and the cover-cache row; no crash row appeared because no crash had occurred.
- Release compilation, unit tests and `lintRelease` passed. Lint: 0 errors, 120 warnings (tooling/SDK/localization/style, no blocking issue). Unit tests passed: queue order/shuffle/fade, discovery policy, crossfade steps including 8 s, natural-order queueing, filename metadata, album path handling, DIDL-Lite parsing and UPnP string policy.
